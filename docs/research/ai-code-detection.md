# AI-generated / AI-assisted code detection — evidence, limits, and a safe design for OJ Sentinel

- **Status:** deep-dive companion to [`landscape.md`](landscape.md)
- **Date:** 2026-10-23
- **Audience:** OJ Sentinel maintainers and course staff
- **Bottom line:** there is no reliable, general-purpose detector of AI-generated student code today. Published code-specific classifiers can work *in distribution* on a known generator/prompt/dataset, but they do not transfer across generators, prompts, courses, or terms, and they are easy to fool with semantics-preserving edits. OJ Sentinel should not ship a binary "AI-generated" verdict. It can ship **weak, explainable AI-assistance indicators** for human triage, and it should invest more in assessment design than in detection.

---

## 1. Definitions (the words matter)

| Term | Question asked | Typical method | Can OJ Sentinel answer it? |
| --- | --- | --- | --- |
| **AI-generated code detection** | Was this whole submission produced by a model? | supervised classifier, zero-shot perturbation, text detector | No, not reliably; ground truth is unknown and mixed authorship is common |
| **AI-assisted code detection** | Did the student use AI for part of the work (completion, explanation, rewrite)? | process logs, edit behaviour, style, LLM judge | Only weakly; OJ snapshots do not include keystrokes/IDE telemetry |
| **Authorship attribution** | Which human (or model) wrote this? | stylometry, AST features, transformers | Not in classrooms at useful accuracy (see §4.3) |
| **Provenance / watermarking** | Did a cooperating generator embed a detectable signal? | logit watermark, variable watermark | No; arbitrary student code contains no watermark |
| **Duplication/provenance matching** | Does this code match known public or historical code? | fingerprint/index matching | Yes, locally, against a corpus the institution owns |

A binary label hides the most important fact: **AI assistance is a spectrum**. A student may write the structure, ask a model to fix a bug, and paste a helper function. A detector trained on "whole solution generated by model X" is answering a different question from "did this student get inappropriate help on this assignment under this course policy". The second question is a *policy* question, not a classifier output.

---

## 2. Why code is a hard target

1. **Low entropy.** Code has strict syntax and a small set of likely continuations; watermarking and perplexity-based detection are weaker than in prose ([SWEET, arXiv:2305.15060](https://arxiv.org/abs/2305.15060)).
2. **Many correct programs.** For a typical OJ problem there are many valid implementations; similarity to a reference solution is not evidence of AI use.
3. **Shared idioms and templates.** Boilerplate (`sys.stdin`, `for i in range`, `if __name__ == "__main__"`) dominates short submissions, so lexical detectors see "AI-like" regularity everywhere.
4. **Semantics-preserving edits are cheap.** Renaming variables, inserting dead code, reordering statements, or reformatting can erase stylistic/watermark signals without changing behaviour ([watermark robustness, arXiv:2403.17983](https://arxiv.org/abs/2403.17983); [Disappearing Ink, arXiv:2507.05512](https://arxiv.org/abs/2507.05512)).
5. **Models are trained on human code.** The "machine style" is partly the style of the public code the model learned from; the boundary is not stable.
6. **Ground truth is contested.** The same submission may be acceptable under one course policy and forbidden under another. Detection cannot know the policy.

Implication: text-detector features (perplexity, burstiness, token-rank distributions) do not transfer cleanly to code; code-specific features help in-distribution but overfit to the generator/prompt/dataset.

## 3. Method taxonomy

| Family | Representative work/tools | Signal | Data needed | Main failure mode |
| --- | --- | --- | --- | --- |
| Text AI detectors applied to code | GPTZero, GLTR, DetectGPT, Sapling, GPT-2 detector | perplexity/curvature/rank patterns | text/code only | near chance on code; prompt-sensitive |
| Supervised code classifiers | Whodunit (XGBoost + stylometry); fine-tuned CodeBERT/CodeT5; AI code stylometry | 100s of lexical/AST/style features or learned representation | labelled human + model-generated code | generator/prompt/domain shift; gameable features |
| Zero-shot perturbation | DetectCodeGPT | stylistic-token perturbation + model scoring | a scoring model; no labels | model-dependent; can be evaded; degrades with new generators |
| Authorship attribution / stylometry | Caliskan-Islam et al.; CodeBERT classifiers | AST/layout/identifier/comment style | multiple samples per author | near chance in classrooms; short snippets; style change |
| Watermarking | SWEET, CodeMark, N-gram watermarks | embedded statistical/identifier signal | access to the generating model | not present in arbitrary code; broken by obfuscation |
| LLM-as-judge | general-purpose LLM prompts ("is this AI-written?") | model's own judgement | an LLM + prompt | unstable, biased, prompt-sensitive, privacy/cost |
| Behaviour/process | Argus; programming-process features | timing, edits, bursts, first-attempt success | process logs/commits | confounds; OJ snapshots are coarse |
| Corpus/provenance matching | GitHub Copilot code referencing; MOSS-style matching | exact/near match to known code | a code corpus/index | only finds known code; not AI authorship |

## 4. Evidence review

### 4.1 Off-the-shelf text detectors on code are near chance

Pan et al. evaluated five widely used AIGC detectors — GPTZero, Sapling, GPT-2 Detector, DetectGPT and GLTR — on 5,069 Python samples (human solutions from Quescol/Kaggle/LeetCode plus ChatGPT-generated variants) across 13 prompt variants. Results (their Table 3 and discussion):

- **GPTZero:** accuracy ≈ `0.497`; under the paper's definitions it had high TPR but very low TNR, i.e. it classified almost everything as human-written. Accuracy barely changed across most variants (`0.4965–0.5108`), with one variant at `0.5824`.
- **DetectGPT:** accuracy `0.4014–0.5354`, i.e. around chance; it misclassified most human code as AI-generated.
- **GLTR:** accuracy `0.4841–0.7693`; highly sensitive to prompt variants (their paired t-test p ≈ `0.0296`).
- **Sapling:** accuracy `0.5425–0.6811`; better than chance on some variants but still far from a usable detector.
- The detectors were sensitive to *how* the code was prompted (function name changes, long/short methods, dead code, etc.), which is exactly the variation a student population produces.

Source: [Pan et al., *Assessing AI Detectors in Identifying AI-Generated Code: Implications for Education*, arXiv:2401.03676](https://arxiv.org/abs/2401.03676).

Two independent warnings reinforce this:

- **OpenAI's own text classifier** reported 26% true positives and 9% false positives on its challenge set, said it is "very unreliable" on code, and was withdrawn on 2023-07-20 due to low accuracy ([OpenAI, archived](https://web.archive.org/web/2024/https://openai.com/index/new-ai-classifier-for-indicating-ai-written-text/)).
- **GPTZero's FAQ** says results "should not be used to punish students", that edge cases exist in both directions, and that accuracy drops for text unlike its training distribution ([GPTZero FAQ](https://gptzero.me/faq)). GPTZero is a prose detector; using it on code is off-label in addition to being empirically weak.

**Conclusion:** do not use GPTZero/GLTR/DetectGPT/Sapling as an OJ Sentinel "AI detector". At best they produce a weak prior that is dominated by prompt/style effects.

### 4.2 Code-specific classifiers: useful in-distribution, not general

| Study | Data / method | Reported result | What it does **not** show |
| --- | --- | --- | --- |
| **Whodunit** ([arXiv:2403.04013](https://arxiv.org/abs/2403.04013)) | 798 human + 798 GPT-4 Python solutions to 399 CodeChef problems; 140 code-stylometry features + XGBoost | F1/AUC `0.91`; excluding gameable features (empty lines/whitespace) still `0.89`; little difference easy/intermediate, slightly worse hard | that it transfers to another model, prompt, course, or language; CodeChef solutions are a special distribution |
| **DetectCodeGPT** ([arXiv:2401.06461](https://arxiv.org/abs/2401.06461)) | zero-shot; analyses lexical diversity, conciseness, naturalness; perturbs stylistic tokens; model-based scoring | +`7.6%` AUC over the supervised baseline in their experiments; model-free and robust to model discrepancies in their setting | that it works on new generators; a 2026 evaluation found it collapsed (see below) |
| **AI code stylometry** ([arXiv:2412.14611](https://arxiv.org/abs/2412.14611)) | transformer encoder, 10 languages, H-AIRosettaMP (121,247 snippets) | average accuracy `84.1% ± 3.8%` across 10 languages | that it generalises to unseen models/prompts; it is trained on a curated dataset |
| **AICD Bench** ([arXiv:2602.02079](https://arxiv.org/abs/2602.02079)) | 2M examples, 77 models / 11 families / 9 languages; robust binary classification under distribution shift, model-family attribution | a benchmark, not a deployed detector | that any current detector is robust; the benchmark's existence argues the opposite |
| **MultiAIGCD** ([arXiv:2507.21693](https://arxiv.org/abs/2507.21693)) | Python/Java/Go dataset covering multiple models/prompts/scenarios | a dataset for training/evaluation | generalisation to a new course or generator |

**Detector half-life.** A 2026 evaluation of eight general-purpose LLM judges and three dedicated detectors, across C++/Java/Python and seven generators, found:

- performance varied considerably across generators and prompting strategies, suggesting some detectors rely on generator-specific artefacts;
- **DetectCodeGPT and GPT-Sniffer achieved accuracy `0.50` but F1 `0.00`** in that evaluation because they classified almost every sample as AI-generated;
- general-purpose LLM judges achieved stronger accuracy/F1 in that study.

Source: [Djire, *Code Detectors Have a Half-Life*, arXiv:2610.01664](https://arxiv.org/abs/2610.01664) (preprint). The result is a warning about metric illusions: high accuracy can hide a degenerate classifier that always predicts one class.

**Conclusion:** a code-specific classifier can be a research instrument on a fixed dataset, but it is not a deployable detector for a course whose models, prompts, assignments, and students change every term. If OJ Sentinel ever trains one, it must be local, validated cross-generator and cross-term, calibrated, and shipped as a *ranking aid*, not a verdict.

### 4.3 Stylometry / authorship attribution: strong in contests, weak in classrooms

- Caliskan-Islam et al. introduced a code-stylometry feature set derived from ASTs and reported **94% / 98% accuracy** for 1,600 / 250 authors on Google Code Jam C/C++ submissions; the features were designed to be robust and applicable to Python ([USENIX Security 2015](https://www.usenix.org/conference/usenixsecurity15/technical-sessions/presentation/caliskan-islam)).
- That result has been widely over-read. A 2026 study fine-tuned CodeBERT on Google Code Jam and on institutional coursework:
  - GCJ: `92.6%` Top-1 for 10 authors; `70.7%` Top-1 (88.2% Top-10) for 1,000 authors.
  - Coursework: `0.2%` Top-1 on a closed-assignment dataset of 690 authors; `0.06%` Top-1 on open-ended assignments over 812 authors — at or below chance.
  - Source: [Yemets & Horváth, *Source Code Authorship Attribution Does Not Generalize from Competitions to Classrooms*, arXiv:2608.00227](https://arxiv.org/abs/2608.00227) (preprint).
- A related study on static vs process evidence found final-code attribution in educational data weak (mean Top-1 `0.094`), with process features improving it to `0.233` and pairwise verification ROC-AUC from `0.556` to `0.752`; the author concludes such models are "appropriate only as instructor-mediated decision support, not as independent proof" ([Horváth, arXiv:2607.07400](https://arxiv.org/abs/2607.07400), preprint).
- Style is also manipulable: RoPGen shows adversarial coding-style transformation can degrade deep authorship attribution, and proposes robust training as a partial defence ([arXiv:2202.06043](https://arxiv.org/abs/2202.06043)). An LLM can imitate or alter style on request, which makes "style drift" weak evidence in an era of AI assistance.

**Conclusion:** do not accuse a student because a stylometry model says "not you". Within-student drift can be a *weak* reason code, never a standalone finding. The contest/classroom gap is large and directly relevant to OJ data.

### 4.4 Watermarking: not applicable to arbitrary student code

- **SWEET** addresses the low-entropy problem in code watermarking by selectively watermarking only high-entropy segments; it improves code-quality preservation and detection over baselines ([Lee et al., arXiv:2305.15060](https://arxiv.org/abs/2305.15060)).
- **CodeMark** hides bit strings in variable names while preserving operational semantics ([Li et al., arXiv:2305.12461](https://arxiv.org/abs/2305.12461)).
- **Robustness is poor.** Simple semantics-preserving transformations such as variable renaming and dead-code insertion can erase watermarks ([Suresh et al., arXiv:2403.17983](https://arxiv.org/abs/2403.17983)); N-gram watermarks are provably breakable under obfuscation under mild assumptions ([Zhang et al., arXiv:2507.05512](https://arxiv.org/abs/2507.05512)).

**Conclusion:** watermark detection only works when the generating model cooperates and the code has not been edited. A student's OJ submission has no watermark from the model they may have used. OJ Sentinel cannot "detect watermarks" in arbitrary code. Do not claim it can.

### 4.5 LLM-as-judge: useful for explanation, not for verdicts

The 2026 half-life study found general-purpose LLM judges stronger than dedicated detectors in its evaluation, but that does not make them reliable:

- LLM judgements are prompt-sensitive and model-version-sensitive; the same code can be judged differently across providers/versions.
- They are expensive and non-deterministic; caching and schema validation are mandatory.
- Sending student code to a third-party LLM conflicts with the project's privacy rule unless the teacher explicitly selects snippets (the existing `docs/INTERFACES.md` already says this).
- An LLM asked "is this AI-generated?" tends to produce a confident narrative; that is the opposite of calibrated evidence.

**Recommended role:** use the AI layer to **explain** a similarity pair, summarise evidence, or diagnose a failing submission — tasks where the model is reasoning over given evidence. Do not ask it to pronounce authorship. If it is used for AI-assistance triage, require a structured output with `insufficient_evidence` as the default and force it to cite concrete lines.

### 4.6 Industry practice: GitHub Copilot code referencing is duplication matching, not AI detection

GitHub Copilot's "code referencing" compares a suggestion plus ~150 characters of surrounding code against an index of public repositories; private repositories and code outside GitHub are not included; matches occur in <1% of suggestions; depending on policy, matching suggestions can be blocked or shown with the matching file URLs and detected licences ([GitHub Docs](https://docs.github.com/en/copilot/concepts/completions/code-referencing)).

This is a **provenance/duplication** feature: it tells the user that suggested code matches known public code so they can decide whether to use, attribute, or remove it. It is not a detector of AI authorship, and it does not help with a student's unwatermarked submission. The transferable design pattern for OJ Sentinel is:

- build a **local index** of code the institution owns (past submissions with permission, instructor solutions, starter code);
- show the matching source and licence/attribution metadata;
- let the human decide;
- keep the index refreshed and scoped (privacy, retention).

### 4.7 Behaviour/process evidence is complementary, not decisive

Argus combines behavioural indicators (time span, commit bursts) with stylistic indicators and an H-score for human triage; it explicitly says a high H-score is never evidence of misconduct ([arXiv:2609.36073](https://arxiv.org/abs/2609.36073)). Process features improved authorship verification in educational data but remained far from proof ([arXiv:2607.07400](https://arxiv.org/abs/2607.07400)). Details are in [`behavior-signals.md`](behavior-signals.md).

**Conclusion:** process/behaviour signals are useful for *ranking* and *context*, especially when code-only similarity is inconclusive. They do not turn AI detection into a solved problem.

## 5. Reliability limits

### 5.1 Base rates make "accuracy" misleading

Even a detector with 90% sensitivity and 5% false-positive rate produces many false accusations when the prevalence of AI-assisted submissions is low. Illustrative calculation:

| Prevalence of AI-assisted work | PPV at TPR 0.90 / FPR 0.05 |
| --- | --- |
| 1% | `0.009 / (0.009 + 0.0495)` ≈ **15%** |
| 5% | `0.045 / (0.045 + 0.0475)` ≈ **49%** |
| 10% | `0.09 / (0.09 + 0.045)` ≈ **67%** |
| 25% | `0.225 / (0.225 + 0.0375)` ≈ **86%** |

At a 5% prevalence, roughly half of "detections" would be false positives even with a good detector. A course with 300 students could produce more than a dozen false positives. This is why the review-budget framing (precision at top-k) matters more than headline accuracy.

### 5.2 Distribution shift and detector half-life

Models, prompts, course assignments, and student populations change every term. A classifier trained on GPT-4 outputs may fail on GPT-5/6, Claude, Gemini, local models, or AI-completion tools; the 2026 half-life study documents exactly this ([arXiv:2610.01664](https://arxiv.org/abs/2610.01664)). Any deployed model needs per-term recalibration and drift monitoring; a static model should be treated as stale after one term.

### 5.3 Short code and low entropy

Short OJ solutions (10–40 lines) give detectors little signal; style features are dominated by problem constraints and boilerplate. OpenAI's classifier was explicitly unreliable below 1,000 characters ([OpenAI, archived](https://web.archive.org/web/2024/https://openai.com/index/new-ai-classifier-for-indicating-ai-written-text/)). Watermarking is weaker in low-entropy code ([SWEET, arXiv:2305.15060](https://arxiv.org/abs/2305.15060)). Do not produce a confident AI score for a 15-line solution.

### 5.4 Obfuscation and editing

Renaming, dead-code insertion, reordering, refactoring, and paraphrasing break watermarks and can degrade classifiers; these transformations are exactly what students do when they "make code their own". Disappearing Ink proves N-gram watermark failure approaches `1 - FPR` after obfuscation ([arXiv:2507.05512](https://arxiv.org/abs/2507.05512)). A detector that only works on unedited model output is not a detector for student work.

### 5.5 Bias

- Liang et al. found GPT detectors systematically misclassify non-native English writers as AI-generated; simple prompting can also bypass the detectors ([arXiv:2304.02819](https://arxiv.org/abs/2304.02819)). Code submissions include comments, identifiers, and problem statements that may carry similar language biases.
- Prior programming experience produces "advanced" style that Argus explicitly lists as a benign cause of elevated scores ([arXiv:2609.36073](https://arxiv.org/abs/2609.36073)). A style-based AI flag can penalise students with prior experience rather than helping them.
- Any deployment should audit false-positive rates across language background, prior experience, and course track; this is difficult without sensitive data, which is another reason to keep humans in the loop.

### 5.6 Benchmark contamination and in-distribution evaluation

AICD Bench and MultiAIGCD exist because earlier datasets were narrow and in-distribution ([arXiv:2602.02079](https://arxiv.org/abs/2602.02079); [arXiv:2507.21693](https://arxiv.org/abs/2507.21693)). A classifier evaluated on the same generator/prompt family it was trained on can look excellent and fail in a new term. Vendor benchmarks are not a substitute for local validation.

### 5.7 Ground truth and policy ambiguity

A submission may be "AI-assisted" but permitted; "AI-generated" but disclosed; or human-written but stylistically unusual. A survey of 116 software-engineering students found cheating perceptions were context-dependent and often tied to unclear guidance and time pressure ([de Souza Santos et al., arXiv:2603.17060](https://arxiv.org/abs/2603.17060)). Detection cannot resolve a policy question, and a false accusation can harm a student's academic record and wellbeing.

## 6. Ethical and legal caveats

1. **Presumption of innocence and due process.** A detector output is not a finding. Provide the evidence to the student, allow an explanation, use a consistent standard, and offer an appeal. Argus's authors explicitly centre false-positive risk and require a structured human-review process ([arXiv:2609.36073](https://arxiv.org/abs/2609.36073)).
2. **No punishment from an automated score.** OpenAI and GPTZero both warn against using their classifiers as primary decision tools; GPTZero says results should not be used to punish students ([OpenAI, archived](https://web.archive.org/web/2024/https://openai.com/index/new-ai-classifier-for-indicating-ai-written-text/); [GPTZero FAQ](https://gptzero.me/faq)).
3. **Distinguish AI use from academic dishonesty.** Course policy may allow AI for some tasks, require disclosure, or forbid it entirely. A detector cannot know which policy applies. The UI should link to the policy and avoid moralised labels.
4. **Transparency.** Tell students that similarity/behaviour/AI-assistance tools are used, what they measure, and what they do not measure. Do not use covert surveillance. OJ Sentinel only has submitted snapshots; do not add IP/device/keystroke collection without an explicit policy decision and legal review.
5. **Data minimisation and privacy.** Process locally; do not send code to third-party detectors/LLMs by default; retain evidence only as long as needed; redact names in reports; follow FERPA/GDPR/institutional rules.
6. **Bias monitoring.** Audit false positives across cohorts and language backgrounds; document limitations. A tool that flags non-native English comments or prior experience as "AI" is not neutral.
7. **Proportionality.** The response should match the evidence: a conversation about code ownership is different from a formal misconduct case. Automated similarity/AI signals should trigger the former, not the latter.
8. **Assessment design is more reliable than detection.** Code interviews, oral explanations, in-class exams, and version-control/process evidence are more robust than after-the-fact classifiers; they also teach better ([Code Interviews, arXiv:2410.01010](https://arxiv.org/abs/2410.01010); [Dickey, arXiv:2505.08244](https://arxiv.org/abs/2505.08244)).

## 7. Safe design for OJ Sentinel

### 7.1 Principles

- **No binary verdict.** Never display "AI-generated" as a fact. Use "AI-assistance indicators" / "authorship signals", with confidence and limitations.
- **Local by default.** No third-party detector APIs; no code uploads. The existing AI layer may send only teacher-selected snippets, per `docs/INTERFACES.md`.
- **Human-in-the-loop.** Every indicator is a reason to look, not a reason to sanction.
- **Explainability.** Each indicator cites concrete lines/features and says what would be a benign explanation.
- **Calibration over accuracy.** Report precision at the review budget, not a headline accuracy; monitor drift.
- **Opt-in.** Off by default; course staff enable it per assignment and decide the policy.

### 7.2 Proposed module: `authorship_signals` (not `ai_detector`)

Inputs:

- submission code + problem metadata;
- the student's prior submissions (same course/term, if available);
- optional behaviour features from the behaviour module (bursts, rewrite jumps, first-attempt success);
- optional teacher-selected context (assignment policy, allowed tools).

Outputs (JSON, versioned):

```json
{
  "schema_version": 1,
  "rid": "...",
  "indicators": [
    {"code": "within_student_style_distance", "weight": 0.3,
     "detail": "distance 2.7 vs own median; 3 prior submissions",
     "evidence": {"features": ["comment_ratio", "ast_node_mix"]}},
    {"code": "paste_marker", "weight": 0.2,
     "detail": "markdown fence and 'Here is' in source", "evidence": {"lines": [1, 2]}}
  ],
  "confidence": "low",             // low | insufficient | none (never high)
  "model": null,                    // null for heuristics; provider/model if an LLM was used
  "prompt_version": null,
  "disclaimer": "Signals are not evidence of misconduct. Human review required."
}
```

Rules:

- `confidence` is capped at `low` unless a local, validated calibration study supports more; do not invent a numeric "AI probability".
- Every indicator has a benign-explanation note (prior experience, external editor, pair programming, lecture template, bilingual comments).
- If the AI layer is asked for a judgement, force `insufficient_evidence` as the default and require line citations; store the model and prompt version. Do not let a free-text LLM response become a label.
- Keep a separate `review_pair`/`diagnose_submission` use of the AI layer; those are explanation tasks, not authorship classification.

### 7.3 Signals worth trying (weak, in order)

1. **Within-student stylometric distance** across ≥3 submissions: layout, comment ratio, naming style, AST node distribution, library/API usage, error-handling patterns. Use a robust distance (median/MAD or shrinkage covariance); do not use a global "AI vs human" classifier.
2. **Process/behaviour indicators** from [`behavior-signals.md`](behavior-signals.md): burst after long inactivity, large rewrite between consecutive submissions, first-attempt acceptance at an extreme cohort percentile. These are confounded but concrete.
3. **Paste/AI-surface markers**: markdown fences, "Here is/Here's", Unicode arrows, inconsistent indentation, comments that explain obvious code, advanced constructs not taught, docstrings on trivial functions, mixed comment languages. These are *very* weak and easily triggered by lecture notes/IDE snippets; show them as "context", not weight.
4. **Optional LLM explanation** of the above (not a verdict): "summarise why this submission is atypical for this student, citing lines; list benign explanations." Teacher-initiated, snippet-scoped.
5. **Do not** use a trained global classifier unless you have a local labelled dataset, a cross-generator/cross-term validation, calibration curves, and a monitoring plan. Even then, ship it as a ranking aid.

### 7.4 Validation protocol

A credible validation set needs:

- **Positive examples:** code generated by several models (at least 3–5 families/versions) with several prompts (zero-shot, chain-of-thought, "make it look human", "refactor this"), plus AI-assisted edits.
- **Negative examples:** human solutions to the same problems, including strong students, prior-experience students, non-native English comments, pair-programming (with permission), template-based solutions, and iterative submissions.
- **Obfuscated positives:** rename/reorder/dead-code/refactor transformations.
- **Metrics:** precision at the review budget (top 20/50/100), recall at that budget, false positives per 100 students, calibration (reliability diagram), and subgroup false-positive rates where lawful.
- **Protocol:** train/validate on one term, test on a later term and a different course; report both in-distribution and out-of-distribution results; freeze the model per term; re-run when the generator landscape changes.

If the validation cannot be done (no labelled data, privacy constraints), **do not deploy a classifier**; ship only transparent heuristics with `insufficient_evidence` as the default.

### 7.5 What the UI should say

- "These are indicators, not proof. Similar code can be legitimate; AI use may be allowed by course policy."
- "This signal compares the submission with the student's own prior work / the class distribution; it does not know who typed the code."
- "Review the cited lines and talk to the student before drawing conclusions."
- Link to the course AI policy and the appeal process.

## 8. What NOT to do (AI-specific)

1. **Do not integrate GPTZero/GLTR/DetectGPT/Sapling as an "AI detector"** for code. The evidence says near chance; the vendors themselves warn against punitive use.
2. **Do not train a global classifier on one term's data and ship it as general.** Detector half-life is real; cross-generator/cross-term validation is mandatory.
3. **Do not call a stylometry model "authorship proof".** Contest results do not transfer to classrooms; short snippets are especially weak.
4. **Do not claim watermark detection.** Student code does not carry a watermark; obfuscation erases it.
5. **Do not send student code to a third-party detector/LLM by default.** Local-only; explicit teacher selection; log provider/model/version if used.
6. **Do not auto-penalise, auto-report, or put an "AI" flag on a transcript.** A false positive is a serious harm.
7. **Do not use "AI-generated" and "academic dishonesty" interchangeably.** Policy and intent are separate questions.
8. **Do not hide the method.** Transparency and a student-response process are part of a legitimate system.
